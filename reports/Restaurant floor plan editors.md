# Version the room, never the seat

Restaurant software keeps a table's identity separate from its drawing, and none of it connects numbered seats to the floor plan: reservation platforms sell table capacity and treat walls as décor, POS systems publish layouts from a back office and record a seat only as an integer on an order line, and design editors draw real rooms (walls with thickness, doors that cut into them, parametric chairs) without giving seats any service meaning. Overcooked's chain from guest to seat to printed menu, kitchen ticket and Service Board therefore has no product to copy, but each category supplies one layer of the answer: stable identity from the POS, real geometry from architects' tools, and back-office change control in which staff edit a draft, publish an immutable version, and service sees only what was published. Overcooked's current model has the first layer and lacks the other two. Its geometry sits on a grid of unspecified scale, walls and doors are unit edges, seats have only a side, combinations and versions do not exist, and `save_floor_layout` deletes and re-inserts every placement with no revision check, which is the silent last-writer-wins failure Milka RIS's own audit rated critical. Because no canvas, Service or ticket code references a layout yet, this is the cheapest moment to change course: keep tables and seat numbers as the stable spine, store geometry in integer millimetres with the grid demoted to a snapping lattice, place seats in each table's own frame so no layout renumbers them, publish immutable versions that each Service pins, keep tonight's joins and table states in service-scoped, server-validated rows, and refuse stale saves rather than merge geometry. On top of that model the editor should work like an architect's tool built for a tablet, with wall, opening, table and fixture tools, visible snapping and live clearances, undo over pure operations, autosaved drafts and warnings that harden into publish blockers, all drawn by one SVG renderer whose service and kitchen modes reuse the same geometry.

## Every category separates the table from its drawing

The three kinds of software build floor plans for different jobs, and the job decides what the plan stores. Reservation platforms sell covers over time, POS systems open checks and route orders, and design editors depict a space. Each stores what its job needs and stops there, so each falls short of what Overcooked needs in a different way.

### Reservation platforms sell capacity and draw walls as décor

Every reservation and table-management platform reviewed uses a 2D drag-and-drop canvas on which a table is an identifier plus a cover range. Resy's web editor asks for a unique Table ID, a Table Type ("Dining, Bar, Patio, High Top"), min/max seats and a shape, and offers "Add Decor (shapes)" for everything else ([Resy](https://helpdesk.resy.com/en_us/floor-plan-on-web-SyTdJuBp9)). The more mature products keep the table record apart from its drawing. ResDiary manages tables as list records with a number, maximum covers, an area and a status, and places them through a separate Table Plan Editor that supports several views per segment ([ResDiary tables](https://help-resdiary.theaccessgroup.com/en/articles/12080722-create-edit-or-delete-your-table); [ResDiary table plan](https://help-resdiary.theaccessgroup.com/en/articles/12080839-create-and-manage-your-table-plan)). Tablein lists every table in a sidebar and ticks the ones already placed ([Tablein](https://help.tablein.com/setting-up-the-floor-plan)), and in Libro "using the same table number across different floor plans will link those tables together as a single entity" ([Libro](https://libroreserve.zendesk.com/hc/en-us/articles/47236864860059-New-Dashboard-Modify-the-Floor-Plan)). Where the visible label doubles as identity, renaming breaks bookings: **in Resy, changing a Table ID unassigns the table's existing reservations** ([Resy ResyOS editor](https://helpdesk.resy.com/en_us/floor-plan-editor-SJ5M493VY)), and Tock makes staff duplicate a table to rename it after a schedule is published ([Tock FAQ](https://tock.zendesk.com/hc/en-us/articles/360044451111-Availability-Planning-FAQs)). Architecture is never structural. ResDiary files walls under its "Walls and Pillars" objects, and Zenchef offers "a decoration" for "the bar, stairs or plants" ([Zenchef](https://help.zenchef.com/hc/en-gb/articles/211671989-How-do-I-add-a-table-to-my-room)).

Layouts are tied to time, and combinations are hand-made lists. Resy activates floor plans per shift and handles a holiday by duplicating a plan and activating the copy for that day ([Resy activation](https://helpdesk.resy.com/how-to-activate-floor-plan-and-edit-table-availability-in-dashboard-for-a-shift-BJEnbPXUd); [Resy single day](https://helpdesk.resy.com/how-to-update-a-floor-plan-for-a-single-day-H1z3v7Ud)). TableCheck assigns each layout to a meal-period "sheet" ([TableCheck](https://support-restaurants.tablecheck.com/hc/en-us/articles/900000835263-Creating-a-table-layout)), and Tock keeps plans inside dated schedules, reassigning existing reservations when a new schedule is published and dropping those that no longer fit into an "Unassigned reservations" bucket ([Tock FAQ](https://tock.zendesk.com/hc/en-us/articles/360044451111-Availability-Planning-FAQs)). None of the platforms infers combinations from adjacency at run time. Tock blocks a combination when any member table is blocked ([Tock combinations](https://tock.zendesk.com/hc/en-us/articles/15126385902612-Setting-up-Table-Combinations-for-Availability-Planning)); ResDiary ranks joins by sell order and offers "temporary joins" that apply to a single booking ([ResDiary joins](https://help-resdiary.theaccessgroup.com/en/articles/12082484-create-your-table-joins); [temporary joins](https://help-resdiary.theaccessgroup.com/en/articles/12304448-create-your-temporary-table-join)); Eat App still labels its manual grouping "Recommended" over its automatic one ([Eat App](https://restaurant.eatapp.co/knowledge/table-grouping)); and Wix's public API stores a combination of a 1–4 table and a 3–6 table as **7–10 covers, a capacity stated rather than summed** ([Wix](https://dev.wix.com/docs/api-reference/business-solutions/restaurants/reservations/reservation-locations/get-reservation-location.md?schema=true)).

Two further lessons recur. The live view constrains the editor: Tablein outlines tables in red when they sit too close "because reservation cards display on tables during service" ([Tablein](https://help.tablein.com/setting-up-the-floor-plan)), Libro warns against tables under 18×18 because the times drawn on them become hard to read ([Libro](https://libroreserve.zendesk.com/hc/en-us/articles/47236864860059-New-Dashboard-Modify-the-Floor-Plan)), and TableCheck added zoom in July 2025 "to reduce the risk of selecting the wrong table, especially on tablets" ([TableCheck](https://support-restaurants.tablecheck.com/hc/en-us/articles/48477328268569-Feature-Updates-Zoom-in-out-on-Floor-View-Relocation-of-Language-field-in-Customer-Profile)). Tablet editing is fragile too, and Resy warns that **unsaved floor-plan edits are lost if the iPad locks, rotates or switches apps** ([Resy](https://helpdesk.resy.com/how-to-create-and-edit-floor-plans-in-the-resyos-app-Hk16bwXUO)). Seats barely exist. Libro draws as many chairs as a table's maximum covers and lets staff rotate them ([Libro](https://libroreserve.zendesk.com/hc/en-us/articles/47236864860059-New-Dashboard-Modify-the-Floor-Plan)), TableCheck can show seat icons "based on table's maximum capacity" ([TableCheck legend](https://support-restaurants.tablecheck.com/hc/en-us/articles/900001286866-Floor-Legend)), and Tock answers "Can guests book different experiences within a single party?" with "No" ([Tock](https://tock.zendesk.com/hc/en-us/articles/22751441190292-Setting-up-Multi-Experience-Tables)). Course progress reaches these platforms second-hand from the POS as three or four coarse stages, and Tock moves a party along "within ~3 minutes" of an item firing ([Tock POS](https://tock.zendesk.com/hc/en-us/articles/23958900436628-POS-Integrations-Automated-Party-Status-Updates)). Tock's model of experiences per table and prepaid tickets is the most tasting-menu-specific in the category, and it is now being folded into Resy ([Restaurant Business](https://www.restaurantbusinessonline.com/technology/reservation-services-resy-tock-are-merging)). SevenRooms' and OpenTable's current editors could not be verified, because their help centres are login-gated or script-rendered.

### POS systems publish layouts and number seats on order lines

POS floor editors are furniture-placement tools, covering shape, size, label and capacity plus barriers and labels, and the documented ones put every change behind an explicit step. Toast builds layouts only in Toast Web, and they reach terminals after "Save, then Publish", with "resync all data" as the fallback ([Toast](https://support.toasttab.com/en/article/Creating-Service-Areas-and-Table-Setup-1493049150430)). Lightspeed K-Series terminals see changes only after a manual "Reload" ([Lightspeed](https://k-series-support.lightspeedhq.com/hc/articles/1260804656729)), and Aloha Cloud commits on-device edits with "Apply Changes" ([Aloha](https://docs.ncrvoyix.com/restaurant/aloha-cloud/using/creating_a_floor_plan)). Identity sits apart from placement. **Toast's API `Table` object carries a GUID, a name, a service area and a revenue center, with no coordinates, shape, seat count or capacity** ([Toast API](https://doc.toasttab.com/openapi/configuration/tag/Data-definitions/schema/Table)), and Oracle Simphony defines tables in a Tables module before placing them on workstation pages, where each "Table #" must match ([Simphony](https://docs.oracle.com/en/industries/food-beverage/simphony/simcg/t_tms_front_of_house_enhanced_dining_tables.htm)). When an integration keys on the display number instead, a rename becomes a deletion: storekit treats a renumbered Lightspeed table as new, and "the old table's QR code stops working" ([storekit](https://storekit.com/docs/guides/integrations/pos/lightspeed/dine-in)).

Seats live on the order, not the map. Toast's `seatNumber` is a positive integer, `0` for an item "shared by multiple guests" or `-1` when no seat was chosen ([Toast API](https://doc.toasttab.com/openapi/orders/tag/Data-definitions/schema/Selection/)), and the POS lets a plate belong to only one seat ([Toast Community](https://community.toasttab.com/t5/restaurant-operations/seat-positions/m-p/13485)), whereas Square splits items assigned to several seats automatically when a check is split ([Square](https://squareup.com/help/us/en/article/8583-manage-seats-in-your-restaurant)). Joining tables makes seat numbers collide, and Aloha turns the dilemma into a setting: with "Pivot seating transfer merges seats" on, same-numbered seats merge, and with it cleared the combined table is renumbered ([Aloha](https://docs.ncrvoyix.com/restaurant/aloha-pos/implementing/field_definitions/store_settings_order_entry_group)). On the kitchen side, Simphony's KDS layout "Chit w/ Seat Separator" groups items by seat, the closest precedent for Overcooked's per-table tickets with seat-level restrictions ([Simphony KDS](https://docs.oracle.com/cd/F14820_01/doc.191/f15055/r_kds_chit_layouts.htm)). The live map is mostly table-level. Toast colours a table red when items are held, yellow when sent and green when fulfilled ([Toast](https://support.toasttab.com/en/article/Creating-Service-Areas-and-Table-Setup-1493049150430)), while Simphony's "enhanced" tables draw status, coursing and alert overlays on their edges, and Oracle tells designers to leave space between tables so the overlays stay visible ([Simphony](https://docs.oracle.com/en/industries/food-beverage/simphony/simcg/t_tms_front_of_house_enhanced_dining_tables.htm)). Simphony also scopes merges to the active layout, where they last "until the layout is deactivated or changed", and warns that unseating a table with a check on it makes the check "lost" ([Simphony](https://docs.oracle.com/en/industries/food-beverage/simphony/sipou/c_tms_table_status.htm)).

Offline, the incumbents avoid conflicts rather than resolve them. Toast relays orders through a single wired "local hub", recommends that "each employee choose a single device to place and update orders", and documents no conflict handling ([Toast](https://doc.toasttab.com/doc/platformguide/platformOfflineModeLocalSync.html)); none of the POS documentation reviewed explains what happens when two devices edit the same check or floor plan. Demand for what is missing shows up in feature requests, where Clover Dining's most-voted request, at **112 votes**, is the ability to label guests' names at the table ([Clover](https://clover.uservoice.com/forums/963884-restaurant/category/510038-clover-dining)). The open-source references follow the same pattern. Odoo 18 stores a table's pixel centre, size, seat count and a `parent_id` for joined tables, has no rotation field, and refuses to deactivate a floor while draft orders exist ([Odoo](https://github.com/odoo/odoo/blob/18.0/addons/pos_restaurant/models/pos_restaurant.py)).

### Design editors draw rooms the way architects do

Interior planners model the part restaurant tools skip, which is the building itself. Floorplanner draws "room by room, or wall by wall", gives walls thickness, and makes "A space enclosed by walls" into a room automatically; doors and windows are dropped onto a wall with a hinge side, and zero-thickness "invisible walls" split an open-plan space into separately labelled rooms ([Floorplanner](https://cdn.floorplanner.com/static/brochures/FloorplannerManualEN.pdf)). Sweet Home 3D cuts a wall wherever a door lands and resizes the door to the wall's thickness ([Sweet Home 3D](https://www.sweethome3d.com/userGuide.jsp)), and in SmartDraw "Doors and windows will automatically snap and rotate with walls" ([SmartDraw](https://waz.smartdraw.com/floor-plan/draw-floor-plans.htm)). Precision comes from layered aids, each with a way out. Sweet Home 3D snaps angles to 15°, Floorplanner rotates in 5° and 15° steps from the keyboard and lets users "Hold S to temporarily disable snap", SmartDraw draws blue guides showing "the distance to the nearest wall or nearest object", and Social Tables' Diagram Check enforces chair-spacing, table-spacing and capacity rules, flagging breaches in red ([Social Tables](https://help.socialtables.com/new-user-interface/diagramcheck)). Event tools add parametric furniture: Amadeus's chair-arrangement tool sets each side's chair count, position, spacing, distance from the table and rotation, with its own undo ([Amadeus](https://help.amadeus-hospitality.com/sales-and-event-management/diagramming/Content/chair-arrangement.html)).

These plans read as rooms because they follow drafting conventions: cut walls filled solid ("poché"), openings shown as gaps in the fill, a door drawn as a leaf plus a swing arc, windows as glazing lines inside the wall, and a hierarchy of line weights summed up as "Cut elements heaviest; swings and annotation lightest" ([Studio Matrx](https://www.studiomatrx.org/students/design-drawing/orthographic-views-and-floor-plans)). Floorplanner ships the same plan in black-and-white, coloured-outline, material-and-shadow and blueprint styles ([Floorplanner](https://cdn.floorplanner.com/static/brochures/FloorplannerManualEN.pdf)). Under the hood, the leading tools keep the document separate from its renderer and sync it through a central authority rather than CRDTs. Figma models a document as `Map<ObjectID, Map<Property, Value>>`, lets the server keep the last value it receives for each property, generates object IDs on the client so creation works offline, and calls true CRDTs unnecessary given a central server ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). tldraw renders shapes as DOM/SVG and culls those off screen, so "a canvas with 10,000 shapes might only render 50" ([tldraw](https://tldraw.dev/sdk-features/performance)), while MURAL moved to canvas only at thousands of elements, after which its share of frames rendered at 30 fps or more rose by 80% ([MURAL](https://dev.to/mural/performant-paintings-building-a-canvas-render-engine-4506)).

### Nobody connects numbered seats to the map

Side by side, the three categories show why Overcooked's requirement is new, because each stops where its business stops.

| | Reservation and table management | Restaurant POS | Floor-plan and event editors |
|---|---|---|---|
| What the plan is for | Selling and assigning covers over time | Opening checks and routing orders | Depicting a real space |
| Table identity | ID, cover range, type and area; placement kept separate in mature tools | GUID, name and area; no geometry in the APIs | A furniture object |
| Seats | A chair count or dots, never numbered | An integer on each order line, never on the map | Chairs per side, with no service meaning |
| Architecture | Décor shapes | Barriers and labels | Walls with thickness, doors and windows that cut them, rooms detected from closed walls |
| Multiple layouts | Tied to a shift, schedule or meal period; duplicated for events | Several per location; activatable section layouts | Files and templates |
| Change control | Save, then activate per shift | Save then publish, reload, or apply | Undo/redo; server-authoritative sync |

Overcooked needs the POS column's identity and change control, the editor column's architecture and chair geometry, and the reservation column's combinations. Identity matters because per-seat menus and tickets must survive every rearrangement, geometry matters because staff must recognise the room and seats need real positions on the Service Board and Kitchen Display, and change control matters because the plan and the live copy must "never silently rewrite each other" ([OC README](README.md)). No product combines the three, so the decisions where they meet have no precedent and need the most care: numbering joined tables, keeping seats stable across layouts, and attaching guests to seats.

## Overcooked fixed identity but kept last-writer-wins saves

Overcooked's floor model is four tables, `area`, `dining_table`, `floor_layout` and `floor_layout_table`, and its strongest decision is already made. Tables are restaurant-wide records with a UUID, a number and a label unique in the restaurant, and a seat count, and the glossary states the invariant that matters most: "The Table sets the Seat count, so Seat numbers stay the same in every Floor layout" ([OC glossary](.docs/glossary.md)). Branded UUIDs, tenant-scoped composite foreign keys and row-level security that lets members read but only admins write mean a table cannot be referenced across restaurants or changed by front-of-house staff ([OC dining_table.sql](apps/supabase/schemas/floor/tables/dining_table.sql)). This is the identity layer Toast, Simphony and Libro converge on, and it addresses Milka RIS's root weakness. MR keyed tables, statuses and merges by **label** and mapped them onto fixed integer board slots, which produced the 15.07 incident in which "activating a new dining room rendered every table dead mid-service", as well as phantom SET signals forwarded to the kitchen ([MR floorMaps.js](../src/utils/floorMaps.js)).

Geometry and persistence are the weak layers. A layout is an integer grid of **4–60 cells per side (default 20×12)** whose `content` JSON holds walls and doors as unit-length grid edges `{x, y, axis, length}` and blocks as labelled rectangles; tables occupy cells and rotate in 90° steps, and a seat is only a side (top, right, bottom or left) plus an `order` list ([OC floor.schemas.ts](packages/contracts/src/floor/floor.schemas.ts)). No document defines the physical size of a cell or what `order` encodes. Geometry validation lives only in the Zod contracts, and even there the footprint check ignores rotation, seat numbers are capped at 20 but never checked against the table's seat count, and walls and doors are never tested against tables, so a door need not sit on a wall ([OC floor.logic.ts](packages/contracts/src/floor/floor.logic.ts)). The database adds only basic column ranges on placements and a check that `content` is a JSON object. Most consequentially, `save_floor_layout` locks the layout row, overwrites the content, **deletes every placement and re-inserts it, and takes no expected-version argument** ([OC save_floor_layout.sql](apps/supabase/schemas/floor/functions/save_floor_layout.sql)). The row lock serialises writers, but the last writer still wins silently, and because placement IDs are regenerated on every save, nothing downstream can safely reference a placement.

Milka RIS's July 2026 audit rated this bug class critical. MR kept every map in one settings blob "written whole on every gesture, unconditional upsert, offline replay with no staleness bound… Two admins editing different maps erase each other's entire work; a stale iPad reconnecting hours later overwrites a redesign with its old blob. No undo, no draft/publish, no history" ([MR audit](../docs/APP_ANALYSIS_2026-07.md)). Overcooked's one row per layout fixes the first half of that sentence, but the stale-iPad half survives, now enforced by the server. The same audit lists the other failures a redesign must design out: a layout switch that is not atomic across three persistence domains, a confirmed switch that "silently skips blocked moves", a combined-table move that makes the party "vanish from board, kitchen tickets and floor", seat IDs such as {1, 2, 3, 5, 6} after a chair drag, and restrictions attached to the wrong seat after a merge ([MR audit](../docs/APP_ANALYSIS_2026-07.md)). Overcooked's product documents already demand the remedies, asking the system to "Prevent two people from unknowingly replacing each other's changes" and insisting that "Editing a Draft Floor Plan must not move Tables in a Live Service" and "Retiring a Table must never remove it from past Services" ([OC product.md](.docs/internal/_archive/product.md)). Yet the schema has no versions, no table retirement, no capacity range and no combination entity. Even the Area default is a single global pointer, weaker than the per-day binding MR added after a 12.08 complaint that the editor would not allow "a different layout for today's service because it wouldn't function on tomorrow's" ([MR floorMaps.js](../src/utils/floorMaps.js)).

MR also leaves assets worth carrying over. Its editor operations are pure `state → state` functions, one renderer serves every surface ("do not fork it — add a mode instead"), its MOVE tool must be armed "so a stray touch can't rearrange the room", seat renumbering commits only once every chair has been tapped in sequence, and chairs are "ALWAYS perfectly distributed — the stored positions only decide ORDER" ([MR FloorMap.jsx](../src/components/floor/FloorMap.jsx); [MR FloorEditor.jsx](../src/components/floor/FloorEditor.jsx); [MR floorMaps.js](../src/utils/floorMaps.js)). Its geometry was richer than Overcooked's, with continuous coordinates, wall polylines whose doors were cut into segments and drawn with swing arcs, zones, planters, and seats with offsets and angles. The rewrite kept the identity lesson and dropped the geometry. The timing is favourable, since the client has no canvas, nothing calls `save_floor_layout`, the Service, Kitchen and Reservations pages are empty shells, and the only seeded floor data is one area named "Dummy Terrace" ([OC layout.repository.ts](apps/client/layers/floor/app/repositories/layout.repository.ts); [OC seed.sql](apps/supabase/seeds/seed.sql)). Every change proposed below costs a schema edit today and a data migration as soon as real layouts exist.

## Put identity on tables, geometry in millimetres and numbering in the table's frame

The proposed model keeps Overcooked's spine and adds the layers it lacks. The table summarises it, and the rest of this section explains the choices that matter.

| Layer | Entity | Holds | Written by, and when |
|---|---|---|---|
| Identity | `dining_table` (extended) | UUID, number, label, seat count, min–max covers, typed attributes, default seat arrangement, `archived_at` | Admin, rarely; retired, never deleted, once referenced |
| Identity | Seat: the pair `(table_id, seat_number)` | A stable address from 1 to the seat count | Implied by the table; never renumbered |
| Room | `area` (extended) | Name, order, room shell (walls, openings, fixed fixtures, zones), numbering reference point and direction | Admin, as a draft that is snapshotted into each published layout |
| Arrangement | `floor_layout` + `floor_layout_table` (draft) | Placements, seat arrangements, movable fixtures, combinations, default sections, `draft_revision` | Admin; every save compares and sets the revision |
| Published | `floor_layout_version` (new) | Immutable JSON snapshot of shell plus arrangement, content hash, version number, publisher, time; index of its table IDs | Publish function only; insert-only |
| Service | Area-to-version pin (future) | Which version each Area uses for one Service | Pinned when pre-service outputs are generated, or at service start at the latest |
| Service | Table and seat state (future) | Lifecycle state, SET, blocks, ad-hoc joins, section overrides, guest-to-seat assignments, movement history | Front of house and kitchen, as server-validated commands |

### Tables carry identity, capacity and the default seat ring

`dining_table` should remain the only thing reservations, tickets, menus and history point at, keyed by its UUID, with number and label freely editable; that is the lesson of Resy's unassigned bookings and storekit's dead QR codes. It needs four additions. The first is an `archived_at` column, because a table referenced by any published version or past Service must be retired, never deleted, and Odoo, Lightspeed and Wix all keep an `active` flag or a list of deleted tables for the same reason ([Odoo](https://github.com/odoo/odoo/blob/18.0/addons/pos_restaurant/models/pos_restaurant.py); [Wix](https://dev.wix.com/docs/api-reference/business-solutions/restaurants/reservations/reservation-locations/reservation-location-object.md)). The second is a cover range (`min_covers`, `max_covers`) separate from `seat_count`, since reservation-side capacity is a range while seat count is the number of numbered chairs. The third is a set of typed attributes (accessible-capable, counter or bar seat, high-top, banquette side, menu tier), which turns an industry gap into a feature: no reservation platform reviewed documents an accessibility flag on tables, yet Overcooked already stores the guest needs to match against. The fourth is a **default seat arrangement in the table's own frame**, so a table placed in a new layout arrives with the same chairs numbered the same way.

A seat is the pair `(table_id, seat_number)`, numbered from 1 to the seat count and never renumbered. Guest data such as menu, language, restrictions and pairing should attach to a guest record that is assigned to a seat for a Service, never to anything computed from geometry. MR lacked this separation, which is how a chair drag produced seat IDs 1, 2, 3, 5 and 6. The same separation lets a party move tables with its seat data intact, as the product vision requires when it says "Allow Seats to move with the Party when the Table changes" ([OC product.md](.docs/internal/_archive/product.md)).

### Geometry moves from grid cells to integer millimetres

Store geometry in **integer millimetres in a coordinate frame local to the Area**, and turn the grid into a snapping lattice of 50 or 100 mm. The grid's real advantage survives because millimetres are integers too, so snapping, validation and overlap tests stay deterministic. What changes is that the rules a dining room is judged by become checkable, because those rules are physical. Tables are bought by size (a 1,219 mm, or 48 in, round seats 5–6), a seated diner's chair takes 457 mm (18 in) behind the table edge, and full-service tables want 1,067 mm (42 in) between edges ([Oak Street](https://www.oakstreetmfg.com/the-ultimate-restaurant-seating-layout-guide-with-real-numbers/); [Restaurant-Furniture.com](https://www.restaurant-furniture.com/resources/guides/restaurant-seating-capacity-guide)). None of this can be checked on cells of unknown size, and no scanned plan can be traced to scale on them. The glossary's definition of a Floor layout as "one arrangement of an Area on a grid" would change accordingly.

The fixed architecture should belong to the Area rather than to each layout. Both Overcooked and MR copy walls into every layout today, so moving one wall means editing every layout of the room, and the copies drift apart. A room shell per Area would hold walls as segments with thickness that share corner nodes, each with a kind (exterior, partition, glass, half-height, or Floorplanner's zero-thickness divider for open plans). It would also hold openings attached to a wall by an offset along the segment and a width, plus a hinge side and swing for doors, along with fixed fixtures, zones and the numbering reference point. Layouts would hold what moves: table placements, movable screens and planters, combinations and sections. Publishing a layout snapshots shell and arrangement into one self-contained version, so a pinned version never changes when the shell is later edited. No source addresses this split directly; it follows from Overcooked's own definition of a layout as an arrangement of an Area. Attaching openings to walls lets the renderer draw swing arcs, lets validation catch a table in a door's path, and lets a deleted wall take its openings with it, as MR's `deleteWall` already did.

Generic labelled blocks should become typed fixtures such as bar counter, pass, service station, banquette, pillar, planter, stairs, host stand and guéridon parking, because the type decides the symbol, whether the object is an obstacle in clearance checks, and whether the kitchen minimap strips it. Zones (dining, bar, terrace, private dining, kitchen) are polygons used for labels, colours and spreading accessible seats through the room. Captain sections change with service and staffing, so they are a separate grouping of tables, following Toast's split between physical service areas and reporting revenue centres ([Toast API](https://doc.toasttab.com/openapi/configuration/tag/Data-definitions/schema/Table)). A table placement carries the table ID, shape, centre point, width, depth and rotation. Every element gets a stable UUID generated on the client (walls and doors have none today), because selection, undo, diffs and any future per-element sync depend on it.

Rotation is the one real disagreement in the research notes. One note favours keeping 90° steps, because axis-aligned tables keep overlap maths trivial and "seat on side N" unambiguous, while the others observe that Resy rotates tables with a drag handle, Lightspeed's L-Series editor uses a free rotation slider, and interior planners snap at 15° ([Resy](https://helpdesk.resy.com/en_us/floor-plan-editor-SJ5M493VY); [Lightspeed L-Series](https://resto-support.lightspeedhq.com/hc/en-us/articles/226405368); [Sweet Home 3D](https://www.sweethome3d.com/userGuide.jsp)). Store rotation as integer degrees, snap to 15° with 90° steps as the default, and define seat sides in the table's own frame so rotation never changes which chair is "top". The cost is overlap tests for rotated rectangles and circles instead of cell sets, which is small at restaurant scale, and the benefit is that a room with one diagonal four-top can be drawn as it actually stands.

### Seats sit in the table's frame; layouts may stand them down but never renumber them

Each placement stores its seat arrangement relative to the table, as an ordered list of seat numbers per side for rectangles and as a ring order with a start angle snapped to 15° for rounds. Positions are derived at render time by spacing chairs evenly, MR's proven rule, so resizing a table never strands a chair. A layout may mark a seat **inactive**, for a four-top pushed against a wall or at the joint of two joined tables, but may never add a seat beyond the table's count. That resolves MR's case where "T9 offers 3 seats under Layout B, only 2 under Layout A" without breaking Overcooked's invariant, because T9 has three seats and Layout A stands seat 3 down ([MR floorMaps.js](../src/utils/floorMaps.js)). Validation must then guarantee two things that are unchecked today: that every active seat is placed exactly once, and that no seat number exceeds the seat count.

Numbering defaults should encode the house convention rather than hard-code one. Fine-dining service numbers seats from a "pivot point", with seat 1 the seat nearest a fixed landmark such as the kitchen door, but the direction is not standard: the US NRAEF ProStart curriculum teaches counterclockwise, while St. Louis Magazine's dining editor describes clockwise ([NRAEF ProStart](https://www.ncrla.org/wp-content/uploads/2025/10/L1CH05_InstrActivityGuide.pdf); [St. Louis Magazine](https://www.stlmag.com/dining/ask-george:-how-do-restaurants-number-their-tables-and-why)). Overcooked should store a reference point and direction per Area, use them to number a table's chairs when the table is created, and have the editor **warn, not renumber,** when a layout rotates a table so that seat 1 no longer faces the pivot, because silent renumbering would detach guest data from the chairs staff expect. Direction belongs on the table symbol as an arrow, since words fail: the Court of Master Sommeliers calls clockwise "to the left", and ProStart calls counterclockwise "to the left" ([CMS](https://courtofmastersommeliers.org/wp-content/uploads/2024/05/Service-Standards-24.1.pdf)). The host-relative order of wine service, in which the guest of honour comes first, then ladies, then gentlemen and the host last, moving clockwise, or plain clockwise for parties of eight or more ([CMS](https://courtofmastersommeliers.org/wp-content/uploads/2024/05/Service-Standards-24.1.pdf)), belongs to the party rather than the layout and can be derived from the ring once the host's seat is known. No Overcooked document says what the current `order` list encodes, and the likeliest reading, by analogy with MR, is the order of chairs around the table, so it should either become an explicit ring order validated to cover every active seat once or be derived.

### Combinations are explicit, versioned, and number the party as one table

Planned combinations should be stored as explicit objects inside a layout version, because whether two tables can be pushed together depends on where they stand. Each records its member tables and a **stored** min–max cover range, like Wix's 7–10 or Access Collins, which sums the members' maximums but lets staff override the total ([Access Collins](https://help-accesscollins.theaccessgroup.com/en/articles/12042286-joined-tables-or-areas)). It also records a priority so single tables are offered first, the seats that go inactive at the joint, and a position map that gives the party one continuous ring of positions, each mapped to a real seat on a member table. The editor can suggest combinations from tables whose edges touch, but the admin's list is authoritative, matching the market's preference for predictable, hand-made combinations. Joins made on the spot during service are service-scoped rows, like ResDiary's temporary joins, and never edit the version. Reservations should store the set of table IDs they occupy rather than a combination ID, so an assignment survives a new layout version and the switch planner can check whether the set is still valid.

The continuous ring is a judgement call to check with the floor team before it is built. It matches the runner's need for one numbering per party, illustrated by St. Louis Magazine's example expo call "Table 33, 1 and 2", while keeping guest data on stable seats of the member tables, so a join can be undone without loss. But no training text, operator interview or POS document found in this research says how fine-dining teams renumber joined tables, and Aloha's setting shows that both practices exist ([Aloha](https://docs.ncrvoyix.com/restaurant/aloha-pos/implementing/field_definitions/store_settings_order_entry_group)).

## Publish immutable versions, and keep tonight in the Service

### Drafts publish versions, and each Service pins one

The back-office POS editors documented here put changes behind a publish or reload step, Odoo refuses structural edits while a session is open, and Wix rejects any update that does not quote the latest `revision` ([Odoo](https://github.com/odoo/odoo/blob/18.0/addons/pos_restaurant/models/pos_restaurant.py); [Wix](https://dev.wix.com/docs/api-reference/business-solutions/restaurants/reservations/reservation-locations/reservation-location-object.md)). Overcooked should combine all three. `floor_layout` keeps the working draft and a `draft_revision`. Publishing validates the draft and writes an **immutable `floor_layout_version`** holding a version number, a full JSON snapshot of shell, placements, seat arrangements, combinations and sections, a content hash, and the publisher and time. Alongside it sits a small index of the version's table IDs, so foreign keys can protect archived tables and the editor can answer "which versions use this table?". Version rows are insert-only, with no client grant to update or delete them. Overcooked's architecture makes authoritative validation cheap, because the Zod floor contracts are already mirrored byte for byte into the edge functions ([OC edge contracts](apps/supabase/functions/_shared/contracts/floor/)). A publish edge function can therefore run exactly the rules the editor shows before a security-definer function inserts the version, following the repository's required order of schema, generated types, contracts, edge functions and client ([OC AGENTS.md](AGENTS.md)).

Versions also settle questions the current documents leave open. "Reset", which in MR restored hard-coded seed geometry that Overcooked does not have, becomes "discard the draft and return to the last published version"; "duplicate" creates a new layout from a version; and "restore" copies an old version into the draft, as the product vision asks ([OC product.md](.docs/internal/_archive/product.md)). A Service pins one version per Area when its pre-service outputs are generated, or at service start at the latest, so printed charts and tickets come from the same document service uses. Until then a future Service follows its Area's default, and publishing a new default first shows which future Services and reservations it affects, as Tock does by surfacing "Unassigned reservations" and Zenchef by warning how many bookings "will need new table assignments" ([Tock FAQ](https://tock.zendesk.com/hc/en-us/articles/360044451111-Availability-Planning-FAQs); [Zenchef](https://help.zenchef.com/hc/en-gb/articles/39180398112157-Live-Availability-Change-your-dining-room-during-service)). The existing rule that a table may sit on only one default layout across Areas becomes the sharper invariant that a table appears at most once across the versions a Service pins. A Service-specific floor plan, a future story in the product scope, is then a fork, meaning a version carrying a `service_id` and its source version, made without touching the reusable layout ([OC product_v2.md](.docs/internal/_archive/product_v2.md)).

### Tonight's state lives in service-scoped, server-validated rows

Everything that changes during service belongs in rows keyed by Service and table, writable by front of house and kitchen, while layout configuration stays admin-only. That covers table lifecycle state, SET, blocks, joins made on the spot, seat swaps, and the guest-to-seat assignments that drive menus and tickets. These rows should be append-only commands that the server validates (seat, move, swap, join, split, clear) rather than mutable fields. Appended commands merge without conflict when offline tablets reconnect, the movement history the product wants comes for free, and a state machine on the server stops a stale offline "free" from overwriting a newer "seated", which is PowerSync's business-rule strategy rather than its default last-write-wins ([PowerSync](https://docs.powersync.com/handling-writes/custom-conflict-resolution)). Switching a Service to another layout should be one transactional RPC that re-pins the version, sorts reservations into MR's categories of move, unchanged, needs table and conflict, and refuses the whole switch if any row is blocked, which fixes both MR's non-atomic switch and its silently skipped moves. Because tables and seat numbers are restaurant-wide, a switch moves drawings, not people. Unlike platforms where a renamed table or a new plan can leave bookings unassigned, it should never unassign a booking whose tables still exist in the new version.

### Refuse stale saves instead of merging geometry

The sync engine is deliberately unchosen, since the repository skeleton omits the offline layer and reserves repositories and gateways as the seam for it ([OC repo-skeleton.shaping.md](.docs/internal/_archive/repo-skeleton.shaping.md)), but the evidence points to one conflict policy for layouts under any engine. PowerSync's default is per-field last-write-wins in the order changes reach the server, and it syncs a JSON column as text replaced whole ([PowerSync](https://docs.powersync.com/usage/lifecycle-maintenance/handling-update-conflicts); [PowerSync JSON](https://docs.powersync.com/client-sdks/advanced/custom-types-arrays-and-json)), so a layout stored as one document is one field. Without a check, the last tablet to reconnect overwrites everything. The save RPC should therefore take the expected `draft_revision`, refuse a mismatch, and return the new revision. On refusal the editor keeps the local draft and offers to keep it as a new draft or take the newer one, the conflict-table pattern PowerSync documents, which meets the roadmap's own bar: "Offline edits either synchronize safely or are visibly refused for a clear reason" ([OC roadmap](.docs/internal/_archive/development_roadmap.md)). An advisory lease shown through Supabase Presence ("editing on iPad 2") prevents most conflicts before they happen ([Supabase](https://supabase.com/docs/guides/realtime/presence)), and publishing happens only online.

The strongest alternative is to store the draft as one row per element so that, as in Figma, two people editing different walls never collide. That pays off only if several admins edit one layout at the same time, which layout configuration rarely needs, and it multiplies tables, policies, generated types and contracts under Overcooked's layering rules; stable element UUIDs keep the option open at no cost. CRDTs are the wrong tool. PowerSync's own Yjs demo calls its compaction function a proof of concept that "will have race conditions", its update history grows with every edit, and CRDT payloads are opaque to the SQL validation and row-level security Overcooked relies on ([PowerSync Yjs demo](https://github.com/powersync-ja/powersync-js/tree/main/demos/yjs-react-supabase-text-collab)). Service tablets need very little by comparison, because they cache the immutable versions their Services pin, compare hashes to detect change, and stream service-state commands.

## Build an architect's editor that survives a dining room

### Tools, snapping and undo from professional planners

The editor should feel like Floorplanner, not a form. It needs explicit tools, with Select as the default that Esc always returns to, Room to drag out a rectangle, Wall for polylines with orthogonal and 15° snapping, Opening to drop onto a wall, Table to place one from the restaurant's table list, and Fixture, Zone and Measure. On desktop each tool takes a single-key shortcut, alongside Floorplanner's conventions of "Hold S" to suspend snapping and Space to pan ([Floorplanner](https://cdn.floorplanner.com/static/brochures/FloorplannerManualEN.pdf)). Selecting an object shows handles and a small toolbar beside it (rotate, duplicate, seats, lock), an inspector takes exact millimetres, and drag-box selection enables align and distribute, as in Planning Pod ([Planning Pod](https://planningpod.com/help-center/using-chairs-and-chair-rows)). Snapping combines the grid lattice, 15° angles, snaps to wall faces and table edges, and **live distance labels to the nearest table or wall**, which show the clearance an admin actually cares about. It must stay visible during the drag, since MR's audit faulted a magnet snap "invisible until finger lift" ([MR audit](../docs/APP_ANALYSIS_2026-07.md)). Category locks let an admin freeze the architecture while arranging tables, or in Floorplanner's words "Lock structurals, information or furniture". Undo and redo run over the pure operation layer, which MR's audit noted is "already pure — an op log is cheap", and follow Figma's rule that undoing, copying and redoing leaves the document unchanged ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)).

Three restaurant-specific pieces sit around the canvas. A table palette lists every restaurant table, ticks those already placed as Tablein does, flags tables already on another Area's default, and places new tables at an offset rather than repeating MR's audit finding that "+ TABLE stamps every new table at the same spot". A seat sub-editor shows seat 1 and the direction arrow and supports MR's tap-in-sequence renumbering. A summary bar keeps seats, tables, accessible seats and area per seat in view, much as Eat App's room summary shows total capacity and table counts ([Eat App](https://restaurant.eatapp.co/knowledge/how-to-know-your-room-details)).

### Touch-first safeguards for tablets on bad Wi-Fi

Tablets have no modifier keys, so snapping needs an on-screen toggle and dimensions need a tap-to-type popover; Sweet Home 3D's online and mobile versions simply drop its type-while-drawing entry of wall lengths and angles ([Sweet Home 3D](https://www.sweethome3d.com/userGuide.jsp)). Moving should require an armed state, through MR's MOVE tool or a long press, while a one-finger drag on empty canvas pans and two fingers zoom, and pen input needs palm rejection, since Excalidraw found that a palm resting on the screen triggers accidental zooms ([Excalidraw](https://plus.excalidraw.com/blog/year-three)). Each gesture should persist once, on release, as MR's renderer does, and every operation should autosave the draft locally so that locking, rotating or backgrounding the iPad loses nothing, which is exactly where Resy fails. Geometry editing stays in the admin area on admin accounts. MR moved it out of the front-of-house floor view into an admin panel, making the service floor "strictly service-only" at a time when it had no enforced roles ([MR plan](../docs/FLOOR_FIRST_PLAN.md)). Overcooked has roles, but the separation still holds, because front of house should adjust tonight's Service, never the reusable room.

### Warnings while drafting, blockers at publish

Validation should warn continuously while a draft is edited and block only at publish, because rejecting an offline draft save would strand queued work. The rules fall into two groups, integrity rules that must hold for menus and tickets to be correct and spatial rules a house can tune. The defaults below come from furniture-vendor rules of thumb and from US and English codes, with imperial originals in brackets.

| Check | Default | Basis | Severity |
|---|---|---|---|
| Tables overlapping tables, walls or fixtures; a table outside the room | None allowed | Geometry | Blocks publish |
| Every active seat placed once; no seat above the seat count; combination members placed; a table on at most one pinned layout per Service | Exact | Data integrity | Blocks publish |
| Chair zone counted in each table's footprint | 457 mm (18 in) from the table edge | Vendors ([Oak Street](https://www.oakstreetmfg.com/the-ultimate-restaurant-seating-layout-guide-with-real-numbers/)) | Built into every clearance check |
| Space between table edges | 1,067 mm (42 in); 1,372 mm (54 in) at rounds | Vendor ([Restaurant-Furniture.com](https://www.restaurant-furniture.com/resources/guides/restaurant-seating-capacity-guide)) | Warns |
| Active service aisle | 1,524–1,575 mm (60–62 in) | Vendor ([Oak Street](https://www.oakstreetmfg.com/the-ultimate-restaurant-seating-layout-guide-with-real-numbers/)) | Warns |
| Aisle between two tables whose chairs back onto it (US) | About 1,270 mm (50 in) between table edges, more beyond 3.7 m (12 ft) of length | IBC as adopted in Minnesota ([Minn. R. 1305.1018](https://www.law.cornell.edu/regulations/minnesota/Minn-R-1305-1018)) | Warns |

Two cautions shape this table. Rules of thumb can fail the building code. The IBC measures an aisle between tables from a line 483 mm (19 in) out from each table edge and requires 305 mm (12 in) of width plus 12.7 mm (0.5 in) for each 305 mm (1 ft) of length beyond 3.7 m (12 ft), except for short stretches used by four people or fewer. Two tables whose chairs back onto the same aisle therefore need about 1,270 mm (50 in) between edges, more than the vendors' 1,067 mm ([Minn. R. 1305.1018](https://www.law.cornell.edu/regulations/minnesota/Minn-R-1305-1018)), so the validator should compute the code width rather than apply the rule of thumb. Jurisdiction matters too. US rules are numeric: at least **5% of dining seats** need tops 710–865 mm (28–34 in) high and a 760 × 1,220 mm (30 × 48 in) clear floor space, spread through the room, on routes at least 915 mm (36 in) wide ([Corada](https://www.corada.com/documents/guidance-on-the-2010-adas/226-and-902-dining-surfaces-and-work-surfaces); [Access Board](https://www.access-board.gov/ada/chapter/ch09/); [ADA §403.5](https://www.corada.com/documents/2010ADAStandards/403-5)). England's Approved Document M is functional, asking that "all users have access to all parts of the facility", with a counter section at 850 mm or lower and an accessible threshold to external seating ([ADM Vol 2](https://assets.publishing.service.gov.uk/media/60b0ea89d3bf7f43560e324a/Approved_Document_M_vol_2.pdf)), and the EU's EN 17210 is functional as well ([CEN-CENELEC](https://www.cencenelec.eu/news-events/news/2021/eninthespotlight/2021-03-18-en-17210-2021-accessible-and-usable-built-environment/)). Overcooked's client defaults to Slovenian ([OC nuxt.config.ts](apps/client/nuxt.config.ts)), so unless a jurisdiction pack says otherwise its numeric checks are house benchmarks, not legal compliance. Slovenian national rules were not researched.

### One SVG renderer, several styles, the same geometry

A restaurant room holds tens to a few hundred objects, well within what tldraw renders as DOM/SVG ([tldraw](https://tldraw.dev/sdk-features/performance)), which makes **SVG** the right medium. It is sharp at any zoom, themeable through CSS and Overcooked's semantic colour tokens (a lint rule bans raw Tailwind colour scales) ([OC lint rules](packages/eslint-plugin/src/nuxt-rules/)), hit-testable and accessible through the DOM, and printable. Canvas pays off only at thousands of animated elements, the scale at which MURAL switched. Keep one renderer with modes, which is both MR's rule and the roadmap's exit criterion that floor previews "use the same core rendering rules as their later operational outputs" ([OC roadmap](.docs/internal/_archive/development_roadmap.md)). Those modes are editing for admins, a printable seating chart for the briefing, the Service Board floor, the Kitchen Display floor and its minimap with the architecture stripped, and a picker for assigning reservations.

Styles are where the plan stops looking like a diagram. The owner's critique that floor plans read as a cheap, abstract diagram maps onto specific missing drafting cues: uniform thin strokes, walls drawn as grid lines, labelled rectangles where symbols belong, and no door arcs or window glazing. A Plan style should therefore draw filled walls with gaps at openings, doors as leaves with swing arcs, windows as glazing lines, three or four line weights, and top-down symbols for chairs, stools and banquettes. A Service style mutes the architecture so status colours and seat chips dominate, at MR's 48 px tap targets ([MR V2 research](../docs/V2_DESIGN_RESEARCH.md)), with overlays each user can toggle, because Zenchef warns that showing too much makes its plan "hard to read" ([Zenchef](https://help.zenchef.com/hc/en-gb/articles/360000256998-How-can-I-customise-the-display-of-my-seating-plan)). Guest detail opens in a side panel, since OpenTable's research found that a guest card covering the plan "takes us out of the context of the shift" ([OpenTable](https://www.opentable.design/article/designing-for-hospitality-and-performance)). A Print style produces the one-page seating chart that St. Louis Magazine calls "the most important organizational tool in a restaurant" ([St. Louis Magazine](https://www.stlmag.com/dining/ask-george:-how-do-restaurants-number-their-tables-and-why)). Because Overcooked generates tickets and fires courses itself, its Service style can show each seat's course and restrictions without delay, which reservation platforms waiting minutes for coarse POS stages cannot.

### Setup accelerators and Overcooked's layer rules

Setup effort is a recurring operator complaint, and SevenRooms reviewers describe floor-plan setup as a "real time investment before going live" ([Capterra](https://www.capterra.com/p/165480/SevenRooms/reviews/)). The cheapest fix is the one every planner shares: upload a PDF or photo of the plan, mark two points a known distance apart, and trace walls over it at adjustable opacity, toggling it off to check the result ([Floorplanner](https://cdn.floorplanner.com/static/brochures/FloorplannerManualEN.pdf)). TableCheck's caveats, that a background image hides the sheet and plan names and makes white table labels hard to read in dark mode, argue for treating the image as an editing aid rather than a backdrop for service ([TableCheck](https://support-restaurants.tablecheck.com/hc/en-us/articles/900000840246-Create-edit-delete-Sections)). Recognising tables in an image, as Eat App's importer does, and iPad LiDAR capture through Apple's RoomPlan, as in magicplan, can come later; LiDAR is documented to struggle with glass, and many restaurant frontages are glass ([Eat App](https://restaurant.eatapp.co/knowledge/floor-plan-importer); [magicplan](https://help.magicplan.app/auto-scan-your-floor-plan); [MAVRiC](https://mavricresearch.com/2020/11/10/magicplan-now-with-added-lidar-%F0%9F%A7%82)). Table templates in standard sizes and one-tap duplication for events cover the rest.

The editor fits Overcooked's client rules as a sub-feature of the floor layer's Layout feature. Pure geometry and operations go in a `layout-editor.logic.ts` module and state and orchestration in composables; pointer and keyboard handling runs through VueUse, because raw `addEventListener` is banned; validation derives from the contracts, with messages in i18n; and the Service and Kitchen floor views are composed in shell pages through props and events, because one domain layer may not import another's composables ([OC client AGENTS.md](apps/client/AGENTS.md); [OC usage-selectors.ts](packages/eslint-plugin/src/nuxt-rules/usage-selectors.ts)). The client has no geometry or canvas library and needs none, since rotated-rectangle overlap, segment intersection and even chair spacing are small, testable pure functions, which is where MR's best code already lived.

## Conclusion

The research reframes the problem. Overcooked does not need a better floor-plan editor than Resy or Toast; it needs a floor model none of them has, because none carries a guest's menu, language and restrictions from a seat to a printed card and a kitchen ticket. The genuinely hard problems are therefore the ones without precedent, namely numbering joined tables, keeping seat identity stable across layouts and versions, and assigning guests to seats, and they should be settled with the people who run service before they are coded. Everything else has a proven answer: identity from the POS, geometry from architects' tools, and change control from back-office publishing.

Sequence matters more than scope. A revision check on `save_floor_layout` closes the critical bug class today at the cost of one column and one argument. Immutable versions must exist before the first Service, ticket or printed menu points at a layout, because adding them later means migrating every reference, and physical geometry with an Area shell must land before the first renderer, because a renderer bakes in its coordinate system. Each is a schema edit now and a migration later, while the editor's polish of snapping, styles and underlays can follow in any order once the model beneath it can be trusted.
